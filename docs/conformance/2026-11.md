# GenAI telemetry conformance, November 2026

Nine frameworks, one scripted model call each, checked against the
OpenTelemetry GenAI semantic conventions as they stood on 2026-11-06. The
table is the output of `spanlint matrix tests/fixtures`; the captures, the
versions and the registry commit are all in this repository, so it can be
regenerated.

## What was measured

Each framework directory under `tests/fixtures/` holds one OTLP JSON export
per instrumentation, produced by the script in `scripts/fixtures/<framework>/`
against a real `gpt-4o-mini` call ("Say hi in one word.", temperature 0, 16
output tokens). `scripts/fixtures/VERSIONS.md` records what was installed
for each capture. Where a framework can be instrumented more than one way,
both exports sit in the same directory and feed the same row.

Spans are attributed to a framework by that framework's adapter
(`spanlint.conformance.ADAPTERS`), so the OpenAI call inside a Traceloop
export is not counted under llamaindex or traceloop. The registry is
`model/gen-ai/registry.yaml` from open-telemetry/semantic-conventions-genai
at commit e6658f1 (2026-11-06), shipped as `src/spanlint/data/gen_ai.yaml`.

The rules are the ones `spanlint check` applies plus one that only makes
sense for adapter-claimed spans, `gen_ai.attributes.missing`:

- `gen_ai.attributes.missing`: the span came from the framework but carries
  no `gen_ai.*` attribute at all.
- `gen_ai.operation.name.required`: a span with `gen_ai.*` attributes but no
  `gen_ai.operation.name`, which every span definition requires.
- `gen_ai.provider.name.required`: an inference, embeddings, create_agent or
  remote invoke_agent span without `gen_ai.provider.name`.
- `gen_ai.deprecated.<name>`: an attribute the conventions have renamed or
  removed. `gen_ai.system` is the one that matters here.
- `gen_ai.operation.name.enum`: an operation name that is not one of the
  documented values. The enum is open, so this is a prompt to look, not a
  violation by itself.
- `gen_ai.span_kind.client` and `gen_ai.span_kind.internal`: the span kind
  the convention gives for that operation is not the one emitted.
- `gen_ai.<attribute>.type`: the attribute is present with the wrong type. An
  integer where a double is declared is accepted, as Weaver does.

Not measured: metrics, log events, recommended attributes that are simply
absent, span names. Each row is one call, so a count of 1 means every span
of that kind, not once in a thousand.

## Where the numbers come from

- langchain: `ChatOpenAI.chat` (CLIENT) and `RunnableSequence.workflow`
  (INTERNAL, `invoke_agent`) are clean. `execute_task ChatPromptTemplate`
  carries an operation name the conventions do not have.
- langfuse: both spans use `langfuse.*` attributes only.
- litellm: the native callback's `litellm_request` span collects five
  findings on its own: it is INTERNAL, it sets `gen_ai.system` and
  `gen_ai.openai.response.service_tier`, it has no `gen_ai.provider.name`,
  and `gen_ai.response.finish_reasons` is the JSON string `["stop"]`. Its
  `raw_gen_ai_request` child has no `gen_ai.*` attribute. OpenLLMetry's
  `litellm.chat` span is clean.
- llamaindex: none of the three framework spans carries a `gen_ai.*`
  attribute. The native bridge puts the request and response into span
  events of its own, and OpenLLMetry's workflow span uses `traceloop.*`.
- meai: one span, conformant except for `gen_ai.response.finish_reasons`
  as the JSON string `["stop"]`.
- openai: the default output sets `gen_ai.system` and
  `gen_ai.openai.response.service_tier` and has no `gen_ai.provider.name`.
  With `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` the span
  is clean.
- semantic_kernel: `chat gpt-4o-mini` is INTERNAL, sets `gen_ai.system` and
  has no `gen_ai.provider.name`. `execute_tool fixtures-greet` is clean.
  The request temperature is missing because the value 0 is dropped as
  falsy; nothing flags an absent attribute, so it is not in the table.
- traceloop: the decorator spans use `traceloop.*` attributes only.
- vercel_ai: with the `OpenTelemetry` integration, `chat gpt-4o-mini` and
  `invoke_agent gpt-4o-mini` are clean and `step 1` carries the made-up
  operation name `agent_step`. With `LegacyOpenTelemetry`,
  `ai.generateText.doGenerate` sets `gen_ai.system=openai.chat`, has no
  `gen_ai.operation.name`, and the outer `ai.generateText` has no `gen_ai.*`
  attribute at all.

The OpenAI, LiteLLM and Vercel captures all send temperature 0 as an
integer (Python passes the literal through; the JS exporter encodes every
integral number as an int). That used to count as a type finding; it does
not any more, matching Weaver.

## Reading the table

Three kinds of finding are mixed in the counts and they do not weigh the
same.

Spec drift. `gen_ai.system` was replaced by `gen_ai.provider.name` and much
of the Python side has not followed: Semantic Kernel, LiteLLM's own callback
and the default output of the upstream OpenAI instrumentation all still emit
the old name. The upstream instrumentation only switches when the
application opts in.

Instrumentation bugs. Two unrelated libraries, one .NET and one Python,
serialise `gen_ai.response.finish_reasons` as a JSON string instead of a
string array. Semantic Kernel and LiteLLM's callback start their inference
span as INTERNAL. Semantic Kernel drops a temperature of 0.

Spec gaps. Vercel's `step N` spans and OpenLLMetry's `execute_task` spans
carry operation names the conventions do not have, because there is no
documented operation for one iteration of an agent loop or one step of a
chain. That is being discussed upstream (semantic-conventions-genai #187
and #81); see [upstream-issues.md](upstream-issues.md).

Frameworks whose only finding is `gen_ai.attributes.missing` (Langfuse,
LlamaIndex, the Traceloop decorators) do not implement the GenAI
conventions on those spans at all. They are not wrong, they are elsewhere.

## Relation to the upstream conformance suite

open-telemetry/semantic-conventions-conformance runs scenario programs
through Weaver live-check against a mock model server and publishes a
report for several dozen GenAI library and instrumentation pairs, and
semantic-conventions-genai keeps reference implementations under
`reference/`. This table is not that. It is smaller, it works from exported
telemetry rather than a live run, and it covers a few things the suite does
not: .NET, Semantic Kernel, Langfuse, the Traceloop decorators, and span
kind. Where both look at the same library the findings agree: the suite
reports the LiteLLM finish_reasons type mismatch and flags Vercel's
`agent_step` as an unknown operation name.
